# AGENTS.md — `hivemind-persona-agent-plugin`

Guidance for AI coding agents (and humans) working in this repository. Read it
fully before making changes. It encodes conventions that are not obvious from the
code and that, if ignored, produce work that will be rejected.

## Repo

An [ovos-persona](https://github.com/OpenVoiceOS/ovos-persona) agent protocol
plugin for [HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core). It
implements `AgentProtocol.natural_language_query`, answering a satellite's query
directly from a configured LLM/solver persona and streaming the answer sentence
by sentence — no OVOS bus, no skills stack. Part of the
[HiveMind](https://github.com/JarbasHiveMind) ecosystem — a protocol for
connecting satellite devices to a hub running
[OpenVoiceOS](https://github.com/OpenVoiceOS). Related repos:
[hivemind-plugin-manager](https://github.com/JarbasHiveMind/hivemind-plugin-manager)
(defines `AgentProtocol`), [ovos-persona](https://github.com/OpenVoiceOS/ovos-persona)
(the solver-chain engine this plugin calls), and
[hivemind-ovos-agent-plugin](https://github.com/JarbasHiveMind/hivemind-ovos-agent-plugin)
(the default agent protocol, backed by a full OVOS skills stack).

## Layout / build / test

- Package module: `hivemind_persona_agent_plugin/` (single `__init__.py` plus
  `version.py`). Tests live in `tests/` (unit) and `tests/e2e/` (hivescope
  round-trip) — check before adding a second test directory.
- Set up a throwaway environment inside your clone; never touch a shared venv:
  `python3 -m venv .venv && VIRTUAL_ENV=$PWD/.venv uv pip install -e ".[dev]" --prerelease=allow`
- Run the suite in the foreground: `python3 -m pytest tests -q`. The e2e test
  in `tests/e2e/` needs `hivescope` and a `hivemind-core` build with QUERY/CASCADE
  support; it self-skips (`pytest.importorskip` / `pytestmark`) when either is
  missing, so a skip there is not a failure.
- `uv`, never `pip`. If latest prereleases fail to install or resolve, that is a
  bug to FIX at the source, not to work around with a pin downgrade.

## Working agreement (org-wide law)

- **Git identity is always** `JarbasAi <jarbasai@mailfence.com>`. Never set a
  per-repo override.
- **Never push `dev` or `master`.** Work on a feature branch and open a
  **draft** PR into `dev`. A human merges. You do not merge your own PRs.
- **Never merge or modify `Release X → master` PRs.** They are the maintainer's
  stable-release mechanism, generated by automation.
- **One commit per PR** (squash before pushing). Conventional commits; `feat:`
  only for a user-visible new capability. `fix:`, `docs:`, `chore:`, `ci:`
  otherwise.
- **Disclose AI authorship.** Every PR/issue/comment an agent writes carries, at
  the top: `> 🤖 Auto-generated by <model> via Claude Code — NOT human-reviewed.
  Verify before acting.` PR bodies are plain human prose (3–6 short paragraphs),
  no tables or section-symbol spray.
- **Never edit someone else's** issue, PR description, or comment. Add a comment
  instead; on your own PRs, edit the body rather than piling on comments.
- Keep durable text (README, docs, PR bodies, comments) timeless and standalone:
  no dates, no "currently/now/new", no meta-commentary about the edit itself.
- No scratch files, committed virtualenvs, `__pycache__`, `.pyc`, `.egg-info`,
  or build artifacts in a PR. `git show --stat` shows only intended files.

## Dependencies

- **Floor pins only** (`>=X.Y.Za1`), bumped when a feature or fix is actually
  needed — with a one-line comment saying why. `pyproject.toml` already carries
  one such comment (`hivemind-plugin-manager` floor held at 0.5.0 pending a
  release of #27) — keep that pattern for future floor bumps. No upper caps
  unless a specific released version is genuinely broken.
- **No lockfiles, ever.** Target the latest alphas (`--prerelease=allow`).
- Everything in `pyproject.toml` (deps, metadata, version — the version is
  attr-derived from `hivemind_persona_agent_plugin/version.py`, never
  hand-edited). Never install from git — depend on a published PyPI alpha.
- Apache-2.0. Do not add GPL/AGPL dependencies.

## Tests

- Adversarial by default. A regression test must **fail before the fix and pass
  after** — prove it by reverting only the source (`git apply -R`, never
  `git stash` across worktrees) and watching the test flip.
- Tests must be mutation-proof: gutting the feature must fail the test. A test
  that only asserts a mock was called, without asserting the real behaviour, is
  weak — note it.
- Never skip a test because an optional dependency is missing (the e2e test's
  `hivescope`/`hivemind-core` skip guards are the documented exception, not a
  precedent for new tests).
- CI green is permission to review, not to merge. A non-trivial change gets an
  adversarial review before it lands.

## Repo-specific rules

- This plugin implements `hivemind_plugin_manager.protocols.AgentProtocol` and
  is loaded by `hivemind-core` at runtime via the `hivemind.agent.protocol`
  entry point (see `[project.entry-points."hivemind.agent.protocol"]` in
  `pyproject.toml`). Do not rename the entry point without checking every
  `server.json` that references `hivemind-persona-agent-plugin` as `agent_protocol`.
- Agent plugins are the modern replacement for solvers. Do not add new
  solver-based code to this repo — query answering goes through
  `Persona.stream()`, not a bespoke solver chain.
- `PersonaAgentProtocol.natural_language_query` is a generator: it must always
  terminate the stream with the `None` sentinel (last line of the method), even
  on exception, or a satellite's query hangs waiting for `hive.query.complete`.
  Preserve that invariant in any change to the streaming loop.
- This repo does not itself do API-key resolution, ACL enforcement, or caching
  — those hot-path concerns belong to `hivemind-core` and
  `hivemind-plugin-manager`. Do not add auth/ACL logic here; if a change needs
  it, it belongs upstream.
- The persona config accepts either a JSON file path (`~` expands) or an inline
  dict (see `__post_init__` in `hivemind_persona_agent_plugin/__init__.py`).
  Keep both forms working in any config-handling change, and keep
  `docs/configuration.md` and `docs/persona_format.md` in sync with the code.
